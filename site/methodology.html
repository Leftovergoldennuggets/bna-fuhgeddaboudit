Methodology

This page documents our complete data processing methodology, including limitations, caveats, and known biases. Transparency is central to this project — we want you to understand exactly how we produced every number on this website.

Data Sources

NHTSA Standing General Order (SGO) Data

The National Highway Traffic Safety Administration requires all companies operating Level 3+ autonomous vehicles to report crashes resulting in injury, airbag deployment, or property damage exceeding $1,000. This creates the most comprehensive public record of AV incidents in the United States.

NHTSA provides two separate files:

  • Pre-June 16, 2025 (Amendment 2): The archived dataset covering reports filed before NHTSA updated their reporting format.
  • Post-June 16, 2025 (Amendment 3): The current active dataset with an updated column structure.

These files contain crashes from all AV companies (Waymo, Cruise, Zoox, Tesla FSD, etc.). We filter for Waymo-only crashes using the "Reporting Entity" field.

Waymo Safety Impact Data Hub

Waymo publishes a curated dataset at their Safety Impact Data Hub. This dataset (CSV2) covers crashes during driverless (rider-only) operation and includes exact incident dates, street-level addresses, and crash type classifications, linked to the corresponding SGO Report IDs.

The Hub data is updated approximately quarterly with a lag of several months. It currently covers crashes through --, while the federal record runs through --.

Which record do we trust as the base?

The federal record. An earlier version of this site built its dataset on top of Waymo's quarterly release, which meant crashes newer than that release were silently absent — at times nearly six months of incidents. We rebuilt the pipeline so that every NHTSA-reported crash enters the dataset the week it's published, and Waymo's release is used to enrich matched crashes with exact dates, street addresses, and classifications. Until that enrichment arrives, recent crashes carry month-precision dates and city-level map locations, and are labeled accordingly. As a transparency check, the two sources have historically matched nearly one-for-one for the periods both cover, and we re-verify the match on every update.

Driverless vs. supervised operation

NHTSA's data includes crashes from two different kinds of operation: driverless (no human behind the wheel — including vehicles with remote assistance, which still drive themselves) and supervised testing (a human safety driver in the driver's seat). All headline statistics on this site cover driverless operation only, for two reasons: it is the product the public actually rides in, and Waymo's published mileage — the denominator for any rate — covers only rider-only driving. The -- supervised-testing crashes on record are not discarded: they can be viewed in the Explore section via a dedicated toggle. We classify operation type from NHTSA's "Driver / Operator Type" field, treating any unrecognized value conservatively as supervised.

Data Processing Pipeline

Our data pipeline runs in five automated steps:

Step 1: Download

We download all three raw CSV files directly from NHTSA and Waymo's public servers. The pipeline includes error detection for cases where URLs may have changed (particularly the Waymo Hub URL, which includes a date range in the filename that changes quarterly).

Step 2: Merge and Clean

This is the core data processing step:

  1. Filter: From the NHTSA data, we keep only rows where Reporting Entity = "Waymo LLC". The full NHTSA dataset includes many other companies.
  2. Harmonize: The pre- and post-June 2025 files have different column names (due to the Amendment 2 → 3 transition). We rename columns from the older format to match the newer format.
  3. Combine: The two NHTSA files are stacked into a single dataset.
  4. Deduplicate NHTSA: Some crashes have multiple report versions (updates filed over time). We keep only the latest version of each report, identified by the Report ID and Report Version fields.
  5. Deduplicate Hub: The Waymo Hub CSV occasionally contains duplicate rows for the same SGO Report ID. We keep the most complete record (prioritizing rows with the most boolean fields populated) and drop duplicates.
  6. Merge: We perform a left join of the Waymo Hub data onto the NHTSA record, using NHTSA's "Report ID" and the Hub's "SGO Report ID". NHTSA is the base — every federal crash is preserved, and Hub fields (exact date, address, crash type) are added where a match exists. Two Hub-only crashes from 2020 (before SGO reporting began) are appended so they aren't lost.
  7. Classify operation: Each crash is labeled driverless or supervised-testing from NHTSA's "Driver / Operator Type" field.
  8. Resolve metro areas: Each crash is assigned to a metro using the Hub's county (when available) or NHTSA's city + state. The mapping covers every county and suburb in Waymo's operating areas (e.g., Tempe and Scottsdale → Phoenix; Mountain View and San Jose → San Francisco Bay Area; Glendale resolves by state, since both Arizona and California have one). Anything unrecognized lands in an "Other" bucket and triggers a loud warning in the pipeline log — crashes are never silently dropped.

Step 3: Compute Statistics

Every number displayed on the website is computed in this step and saved to a JSON file. This includes:

  • Total crash counts and city breakdowns
  • Time-of-day analysis (rush hour, late night, daytime/nighttime splits)
  • Crash type distributions
  • Severity indicators (police-reported, injury-reported, airbag deployment, serious injury, fatality count)
  • Location type analysis (intersection, street, parking, highway)
  • Day-of-week patterns

Step 4: Generate Map Data

Each crash record is geocoded and converted into a simplified JSON object for the Leaflet map. Geocoding queries use the crash's own city from the federal report (a Tempe intersection is searched in Tempe, not metro-core Phoenix), and results must land near that city's centroid to be accepted. Every marker carries a location-precision tier, flagged in its popup:

  1. Street level: the full intersection or address from Waymo's Hub release matched (e.g. "7th Street & Market Street").
  2. Road level: only one of the two named streets matched — the marker sits on the right road, but the exact point along it is approximate.
  3. City level: recent crashes not yet covered by the Hub have no public address (NHTSA redacts them), so they're placed near the centroid of the city NHTSA names, with a small random offset.
  4. Metro center: the rare last resort when even the city can't be geocoded.

Results are cached locally to avoid repeated API calls. Currently --% of mapped driverless crashes (-- of --) are placed at their real street location; the share rises automatically each time a quarterly Hub release adds addresses for recent crashes. Each record also includes severity flags (has_injury, is_serious, is_vulnerable_road_user) used for color-coding markers on the map.

Step 5: Extract Serious Incidents

Crashes involving moderate, serious, or fatal injuries are extracted into a separate file with their full NHTSA narratives, enabling the detailed incident view on the map.

Crash Circumstances Analysis

In addition to the core statistics (counts, severity, timing, geography), we analyze the circumstances of each crash using fields from the NHTSA Standing General Order reports.

Speed at Time of Crash

The NHTSA report includes a "SV Precrash Speed (MPH)" field recording the subject vehicle's speed at the time of the crash. We use this field to compute the speed distribution displayed on the website. Of -- total crashes, nearly all have valid speed data.

We bucket speeds into six ranges: 0 mph, 1–5 mph, 6–15 mph, 16–25 mph, 26–35 mph, and 36+ mph. The median and mean are computed from the raw values. The finding that --% of crashes occur at 0 mph is derived directly from this field with no adjustment or interpretation.

Pre-Crash Movement

The "SV Pre-Crash Movement" field describes what the Waymo vehicle was doing immediately before the crash (e.g., stopped, proceeding straight, making a turn). The "CP Pre-Crash Movement" field describes the other party's movement. We report both for context.

These fields describe the physical movements of the vehicles, not legal fault or responsibility. A vehicle classified as "stopped" at the time of contact may or may not bear any responsibility for the circumstances that led to the crash.

Crash Type Classification

Crash types (e.g., "V2V F2R", "Pedestrian") come from Waymo's Safety Impact Data Hub, not from NHTSA, so they exist only for the -- crashes the Hub has covered so far; the most recent -- crashes are shown as "pending classification" until the next quarterly release. (For the vulnerable-road-user counts we additionally fall back to NHTSA's "Crash With" field so recent pedestrian/cyclist/motorcycle crashes aren't undercounted.) Waymo classifies each crash into one of 11 categories. We translate these codes into plain English for readability:

  • V2V F2R → Rear-end collision
  • V2V Lateral → Side-impact collision
  • V2V Backing → Backing collision
  • V2V Head-on → Head-on collision
  • V2V Intersection → Intersection collision
  • Single Vehicle → Single vehicle
  • Secondary Crash → Secondary crash
  • Motorcycle → Motorcycle
  • Cyclist → Cyclist
  • Pedestrian → Pedestrian
  • All Others → Other

Limitations and Caveats

Crash Locations and Geocoding

NHTSA redacts both GPS coordinates and street addresses from its public files. Street-level addresses come from Waymo's Safety Impact Data Hub release ("Location Address / Description"), which we geocode using OpenStreetMap's Nominatim service with a multi-strategy approach (intersection parsing, direct address lookup, metro sanity checks).

Current accuracy: --% of mapped driverless crashes (-- of --) are placed at their real street location. The remaining -- — mostly recent crashes the Hub hasn't covered yet — are placed at city level and flagged as approximate, both on the map and in this statistic. Accuracy varies by city:

  • San Francisco: --%, Los Angeles: --%, Austin: --%
  • Atlanta: --%, Phoenix: --% (some reports have less detailed addresses; newer metros are lower until the Hub covers them)

Geocode results are cached in geocode_cache.json to ensure reproducibility and avoid repeated API calls.

Reporting Thresholds

The NHTSA Standing General Order has been amended three times since its original 2021 release. The most significant change for this dataset occurred on June 16, 2025, when the Third Amended SGO took effect. Key changes include:

  • Property damage threshold: The amended order added a threshold for property-damage-only crashes involving ADS vehicles, meaning very minor incidents that would have been reported under the previous rules may no longer be reported
  • Reporting timeline: The deadline for reporting the most serious crashes was extended from one calendar day to five calendar days
  • Duplicate reporting: When multiple companies are involved in the same crash, only one entity now needs to report (unless they have materially different information)

This means the dataset is not perfectly uniform across time. Crashes reported before June 2025 were filed under a lower reporting threshold than those reported after. When interpreting trends over time, this difference in reporting requirements should be considered.

For our analysis, we include all crashes from both periods. Where relevant, we note the reporting period distinction.

Severity Assessment

We report severity using four independent boolean indicators rather than a composite score:

  • Police-reported: Whether law enforcement responded to the scene
  • Injury reported: Whether any injury (of any severity) was reported
  • Airbag deployed: Whether any vehicle's airbag deployed
  • Serious injury: Whether a suspected serious injury was reported

We deliberately avoid creating composite "severity scores" because the weighting of different factors would be arbitrary and potentially misleading.

One nuance: the four boolean indicators come from Waymo's Hub release, so they're unknown for the most recent crashes. Their percentages are therefore computed among crashes with a known value, not the full total. Injury-severity classifications (minor / moderate / serious / fatal), by contrast, come from NHTSA's own "Highest Injury Severity Alleged" field and cover essentially every crash.

A Note on Crash Types and Fault

The crash type classifications in this dataset (e.g., "rear-end collision," "side-impact collision") describe the physical dynamics of the collision — where and how contact occurred between vehicles. They do not indicate who was at fault. NHTSA Standing General Order reports do not assign legal fault or determine responsibility.

In the majority of crashes in this dataset, the Waymo vehicle was stationary or moving at low speed at the time of contact. The crash type describes what happened physically, not why.

Waymo Safety Comparisons

The statistics comparing Waymo to human drivers (e.g., "90% fewer serious crashes") come from Waymo's own peer-reviewed research paper published in the journal Traffic Injury Prevention. While the paper has undergone peer review, it is important to note:

  • The study was authored by Waymo researchers
  • The comparison benchmarks may not perfectly match Waymo's operating conditions (urban environments, specific cities, time of day, weather)
  • Autonomous vehicles currently operate in a limited set of conditions that may be systematically different from the average human driving environment

Crash Circumstances and Fault

This website reports the circumstances of each crash — vehicle speeds, pre-crash movements, crash types, and involved parties — as recorded in the federal crash reports. We do not make fault determinations.

A Waymo vehicle recorded as "stopped" at the time of contact was physically stationary, but this does not necessarily mean the other party was at fault. Similarly, a crash classified as a "rear-end collision" describes the physical configuration of impact, not the cause. Fault determination requires investigation beyond what is available in the NHTSA dataset.

Readers should interpret crash circumstances as descriptive — what happened — rather than prescriptive — who was responsible.

Dataset Coverage

Our headline count (-- driverless crashes) is larger than the count on Waymo's own Hub for two reasons: we include the -- recent federal reports the quarterly Hub release hasn't reached yet, and we count from the federal record rather than Waymo's curation. For the periods both sources cover, they match nearly one-for-one. The -- supervised-testing crashes are excluded from headline statistics (Waymo's published mileage doesn't cover them, so no meaningful rate can be computed) but remain explorable on the map.

Mileage Data

Miles-driven data by city comes from Waymo's Safety Impact Data Hub, which publishes cumulative rider-only miles for each operating city. We use this data to compute crash rates per million miles. These rates allow for more meaningful comparisons across cities than raw crash counts, since cities with more miles driven will naturally report more crashes.

The mileage growth timeline displayed on this website was compiled by Anders Eidesvik from Waymo press releases, public statements, news articles, and archived snapshots of the Waymo Safety Impact Data Hub captured via the Wayback Machine. Waymo does not publish a historical time series of cumulative miles, so each data point was individually sourced and verified. Full source URLs are documented in our data files.

The full mileage milestone dataset, including source URLs for each data point, is publicly available as a Google Sheets document.

Waymo currently publishes per-city mileage only for its four longest-running markets (Phoenix, the San Francisco Bay Area, Los Angeles, and Austin). For newer markets — Atlanta, Miami, Dallas, Houston, San Antonio, Orlando, and Nashville — no mileage has been published yet, so we cannot compute crash rates there.

Temporal Limitations

Crash time data comes from the "Incident Time" field in the NHTSA reports. A small number of records have missing or unparseable times, which are excluded from time-of-day analyses. The overall coverage is high (typically >99% of records have valid time data).

Automated Updates

This website is designed to be "evergreen" — every statistic is computed from data, and the entire pipeline re-runs automatically every Monday.

The GitHub Actions workflow:

  1. Runs the unit test suite (the pipeline never publishes from broken code)
  2. Downloads the latest data from NHTSA and Waymo — the quarterly Waymo URL is auto-detected by probing recent quarter end-dates, so no manual URL updates are needed
  3. Runs the full processing pipeline and validates the output (crash counts must never shrink or go backwards in time)
  4. Commits and pushes any changes, which triggers a site deployment

The one task that still requires editorial judgment: when Waymo announces a brand-new metro, it must be added to the metro registry in the configuration file. Until then, crashes from an unmapped city still appear in the totals and on the map under an "Other" bucket, and the pipeline log calls them out.

Reproducibility

To reproduce our analysis:

  1. Clone the repository
  2. Install dependencies: pip install -r requirements.txt
  3. Run the pipeline: make data
  4. View the results: make serve

Geocoding results are cached in geocode_cache.json (committed to the repository), so map layouts are identical across runs without re-querying the geocoding service. The pipeline's core logic — metro mapping, operation classification, date parsing, merge behavior — is covered by a unit test suite (pytest tests/) that runs in CI on every change.
